# ADR-001: Estrategia Multi-Tenant

**Estado:** Aprobado
**Fecha:** 2026-07-19
**Autor:** Marco Apolonio — Founder & Technical Lead, SMARTPROMARCO GROUP

---

## Contexto

SMARTPROMARCO debe soportar múltiples empresas, escalar desde una PoC hasta
clientes Enterprise, y cumplir distintos niveles de aislamiento de datos
según el perfil de riesgo del cliente (PyME, Enterprise, Gobierno/Banca/Salud).

## Decisión

Arquitectura híbrida evolutiva, no un único modelo para todos los clientes:

| Tipo de cliente | Arquitectura | Motivo |
|---|---|---|
| PoC / Demo | Shared Database + `tenant_id` | Simplicidad y velocidad de desarrollo |
| PyME | Shared Database + `tenant_id` + Row Level Security | Bajo costo, escala sin migrar |
| Enterprise | PostgreSQL Schemas por tenant | Mayor aislamiento y mantenimiento |
| Gobierno / Banca / Salud | Base de datos dedicada | Máximo aislamiento y cumplimiento normativo |

Para la fase actual (PoC): **Shared Database + columna `tenant_id` obligatoria**
en toda tabla de negocio. Toda consulta filtra siempre por `tenant_id`.

## Consecuencias

- Desarrollo más rápido en la PoC.
- Menor costo operativo para clientes pequeños.
- Ruta clara de migración a esquemas o bases dedicadas sin cambiar la lógica
  de negocio (el `TenantRepository` es el único punto que cambiaría).
- Compatibilidad con futuras necesidades regulatorias (ISO 27001/42001, datos
  gubernamentales).

## Implementación (trazabilidad código ↔ decisión)

| Elemento | Ubicación |
|---|---|
| Columna `tenant_id` obligatoria | `src/modules/auditoria/models.py` (Evidencia, MatrizTrazabilidad, HallazgoAuditoria), `src/modules/usuarios/models.py` (Usuario) |
| Entidad Tenant | `src/modules/tenants/models.py` |
| Resolución de tenant activo (API Gateway de la PoC) | `src/api/dependencies.py::get_tenant_activo` |
| Middleware JWT → tenant_id | `src/core/security.py::get_current_user`, `TokenPayload.tenant_id` |
| Test que verifica el filtro por tenant | `tests/test_auditoria.py::TestEvidenciaKPIs` |

## Alternativas consideradas

- **Base dedicada desde el día 1**: descartada para el PoC — sobre-ingeniería,
  retrasa la validación de producto sin beneficio de aislamiento real todavía
  (no hay datos sensibles de clientes reales en esta fase).
- **Sin `tenant_id`, un despliegue por cliente**: descartada — no escala
  operativamente antes de tener ingresos que lo justifiquen (ver Fase 5 SaaS).
